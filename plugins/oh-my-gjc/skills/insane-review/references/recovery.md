# 번들 insane-review의 전송 경계와 회수

`pack_and_ask.py`의 새 실행마다 기존 `run_tag`로
`.insane-review/runs/run_<tag>.json`을 남긴다. `runs/`는 소유자 전용 `0700`,
journal은 `0600`이다. 임시 파일을 fsync하고 원자적으로 게시하며, 읽을 때 경로의
심볼릭 링크, 소유자/권한, 하드 링크, 스키마, 중복 키와 턴 식별자를 검증한다.
같은 사용자 권한으로 journal을 다시 작성하는 악성 프로세스를 인증하는 장치는 아니다.

## 전송과 재시도

- `prepared`: 아직 전송 시도 전. `--retries N`은 이 단계의 준비 실패에만 적용된다.
- `unknown`: 전송 버튼을 누르기 **전에** 디스크에 기록하는 상태. 클릭 오류나
  요청 턴 미관찰은 미전송의 증거가 아니다. 자동 재전송/Enter 폴백은 없다.
- `observed`: 정확한 요청 본문 해시·run marker·사용자 턴·대화가 관찰됐다.
- `complete`: 정확한 assistant 턴의 완료 응답을 검증하고 저장했다.

이는 한 실행의 클라이언트 전송 시도를 한 번으로 제한하는 장치다.
서버의 exactly-once 처리를 보장하지 않으며, 사람이 별도의 새 실행을 시작하면 새 요청이다.

## 회수 전용 실행

```bash
python3 "$IR" --harvest-only .insane-review/runs/run_<tag>.json --max-wait 1200
# 동일한 별칭:
python3 "$IR" --resume .insane-review/runs/run_<tag>.json
```

`$IR`은 스킬/커맨드의 suite-root binding 검증으로 얻은 경로다.
`--max-wait`, `--stream`, `--council`만 함께 지정할 수 있다.
새 브라우저 기동, 로그인, 패킹, 첨부, 컴포저 조작, 질문 전송, 모델 재선택,
추론 강제 종료를 하지 않는다. 기존 CDP의 전용 프로필 증명과 공유 리스는 필요하다.
기존 lane의 `harvest`/`salvage`를 대체하거나 lane 상태를 읽지 않는다.

journal에 **대화, 요청 본문 해시·run marker·기준선, 검증 모델**이 없으면 회수도 중단한다.
클릭 뒤 DOM 오류로 사용자 턴 ID를 기록하지 못했어도, 결속한 대화에서 위 증거가
모두 일치하는 단 하나의 요청을 확인하면 그 ID를 기록할 수 있다. 대화 URL이나 가장
최근 답을 추측해 채워 넣지 않는다. 기록한 요청 바로 다음 assistant만 허용하며, assistant가
아직 관찰되지 않았었다면 그 요청에 인접한 단 하나의 응답을 결속한다.
다른 대화/요청, 재생성된 응답, 추가 질문, 중복 ID, 불완전한 DOM은 거부한다.

## 코드 동일성과 출력

journal은 패킹본 SHA-256과 **실제로 패킹된 파일 목록·각 파일의 SHA-256**을 보존한다.
Markdown/XML/plain의 파일 헤더를 repomix가 보고한 전체 파일 수와 대조해 목록을
확정한다. 명시적으로 포함한 ignored 파일도 그대로 검사한다. 패킹 도중 수정된 파일은
그 pack에 결속하지 않는다. 전송 직전과 회수 완료 시 같은 파일들의 내용을 다시 검사한다.
포함 파일의 수정/삭제, 패킹 변조는 이전 리뷰를 현재 해당 코드의 판정으로 저장하지 못하게 한다.

패킹 대상에 없는 `node_modules/.bin`, `.venv`, `.env`, `.gjc` 등은 순회하거나
해시하지 않는다. 그곳의 심볼릭 링크나 런타임 변화는 해당 리뷰를 무효화하지 않는다.
반대로 **패킹 목록에 든** 파일의 심볼릭 링크는 거부한다. 리뷰의 범위는 기록된 목록이다.
나중에 추가한 파일이나 다른 범위를 포함하려면 새 리뷰를 실행해야 한다.

타임아웃/쿼터/빈 응답/거부문/잘못된 턴은 응답 파일로 저장하지 않는다. 완료 응답은
원자적으로 `0600` 게시하며, 기존 파일을 덮어쓰지 않는다. journal과 pack은 실패 뒤에도
보존한다. `--delete-pack`은 성공 응답을 기록한 뒤에만 삭제하며, 삭제한 pack을 요구하는
이후의 회수/후속 검증은 중단된다.

`--followup`은 **새 질문**이다. journal을 가리키는 새 형식의 응답 파일을 넘기면
기존 완료 응답과 코드 동일성을 검증한 뒤 새 요청 journal에 원본 증거를 상속한다.
코드가 달라졌으면 새 코드 리뷰를 시작해야 한다. URL만 넘기거나 구형 응답을 사용한
후속 질문은 검증 모델/원본 코드 증거가 없어 harvest-only 재개 대상이 되지 않는다.
